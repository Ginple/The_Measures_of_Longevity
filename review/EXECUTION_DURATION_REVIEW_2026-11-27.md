## 已观察到的事实

1. 前一轮在 `ccd72f6` 推送后结束答复，虽然项目和大量研究债仍未完成。**这是任务管理上的提前收束**：把一次研究增量和快速验证当成一个适合停下的节点；用户要的是连续实质推进，并非每一小增量就询问或终止。提交及 Linear 更新是检查点，不应自动成为停止条件。
2. 仓库提交记录显示 2026-11-27 10:25:45–10:45:26 UTC 间有多个增量提交，相邻提交间隔约 1–9 分钟。**提交间隔不是运行耗时，更不是全部研究持续时间**；没有历史各阶段完整 wall-clock 遥测，不能精确量化过去每轮运行时长或证明某一全局时间限制。
3. 本次重新配置虚拟环境后，`scripts/run_validation.py` 的一次实测 wall-clock 约 4.3 秒，输出工程 82、实验 16、pilot 21 通过。它是**离线软件契约检查**，内容为单元测试、跨种子及搬移复现、看板及有限 Markdown 链接检查；没有系统检索、患者数据复算或外部审稿。4.3 秒是所做工作的实际耗时，不是整个研究的合理完成时间。`/usr/bin/time` 在此环境不存在，以上改用 Python monotonic 测量。
4. 验证脚本对各子测试和 CLI 设 120 秒，对子进程套件设 180 秒上限；这些是**单进程超时保护，不是期望执行时间**。本次全部正常退出且未触发超时，不能据此说以前任务都被超时杀死。
5. 本次恢复的文件快照包含上一轮内容，但初始本地 Git 只指向基线、先前提交在远端，`.venv` 不保留。已 fetch 当前分支，在同步索引前逐一核对远端 382 个 blob：无缺失、无字节差，且无暂存更改，然后仅以 mixed reset 对齐分支/索引，未覆盖工作文件；重新安装开发依赖。环境重建会增加启动步骤，但不是上轮主动结束的证明，也不能假定每次均以同样方式恢复。

7. 本环境对终端外连有主机限制。公开 Borealis 页面和代码可通过页面读取，直接在终端拉取对应主机未被允许；目前没有模型数组/R 实测。不能把待办写成自动进行中的后台任务。

## 即刻改变的执行方式

- 多条工作流持续交错：原始论文与版本审读、数学反例、可用代码静态/动态审计、书稿依赖和工程验证。一次快检成功后转入下一条，而不是把快检当整体完成。
- 每项记录：来源版本、已读位置、原文/推导、对立解释、结果边界、实际执行状态、下一操作及其依赖。未完成标 open，不以下载页可用代表数据已读。
- 用增量提交和 Linear 状态保存现场，**不人为 sleep 或启动空转进程**来制造时长；不将计划写成已运行。需要长时运行的真实命令使用进程工具、明确日志和退出状态；平台本身的会话/工具边界无法由仓库保证永久后台推理。
- 对无法自主完成的环节明确阻塞（如账单、研究者授权、真实独立外审）；其他不依赖阻塞的任务继续做。任何结尾须列明停止时实际状态，不声称“正在后台继续”，除非有真实运行的进程且已检验。
